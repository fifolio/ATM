## Abstract

Automission (ATM) is a full-stack, terminal-centric web application that delivers real-time and near-term cryptocurrency market intelligence through a command-line interface (CLI) paradigm rendered in the browser. The system integrates multi-source market data acquisition, large language model (LLM) reasoning via Google GenAI, structured prompt engineering, and a usage-metered resource economy (RPU/MRPU). It provides users with hierarchical analytical products: high-level market insights, directional coin rankings (bulls/bears), discrete long/short signals, and granular single-asset trade forecasts that include entry, stop-loss, take-profit levels, risk-reward ratios, confidence scores, and explicit risk disclosures.

Architecturally, ATM is implemented as a React 19 + TypeScript + Vite single-page application (SPA) deployed on Vercel, backed by Appwrite for authentication and document storage, and orchestrated through Zustand state management. The design prioritizes deterministic command parsing, rate-limited AI inference, transparent reasoning chains, and academic-grade output formatting using ASCII tables (cli-table3). This document constitutes a complete technical and methodological exposition intended for academic review, peer examination, and professional engineering evaluation.

## 1. Introduction and System Overview

Automission (ATM) is conceived as an intelligent decision-support system for cryptocurrency market participants. Unlike traditional technical analysis dashboards or black-box trading bots, ATM exposes its reasoning through a transparent, command-driven interface that mimics professional quantitative research terminals.

The primary user experience is a persistent terminal emulator. Users issue natural-language-style commands prefixed with `atm`, and the system responds with structured, multi-table ASCII reports that contain both quantitative metrics and qualitative AI-generated justifications.

**Key value propositions:**

- Multi-horizon market intelligence (macro insights → directional rankings → single-asset trade plans).
- Explicit confidence scoring and risk flag enumeration.
- Metered consumption model that encourages disciplined usage.
- Fully auditable reasoning chains generated by an LLM under controlled prompting.
- Zero-install web accessibility while preserving a professional CLI aesthetic.

The system is currently at version **4.2.4** and is deployed at [https://automission.vercel.app](https://automission.vercel.app).

## 2. Design Philosophy and Academic Motivation

The design of ATM rests on three interlocking principles drawn from quantitative finance, human-computer interaction, and machine learning systems research:

1. **Transparency over opacity**  
   Every recommendation is accompanied by a reasoning summary, detailed rationale, red-flag list, and underlying assumptions. This aligns with the growing academic and regulatory demand for explainable AI (XAI) in financial decision support.

2. **Hierarchical information architecture**  
   Information is delivered in progressive layers of granularity, mirroring the classical top-down analysis workflow used by institutional research desks (macro → sector/theme → single name → trade construction).

3. **Resource-constrained intelligence**  
   By introducing a finite Request Processing Unit (RPU) budget, the system forces users to treat AI inference as a scarce resource, analogous to computational budgets in high-frequency trading research environments.

These principles collectively aim to elevate the system beyond a simple chatbot into a research-grade analytical platform suitable for academic scrutiny.

The architecture follows a classic three-tier pattern adapted for a modern SPA:

- **Presentation Tier**: Terminal component, command parser, and response renderers.
- **Application Tier**: Orchestration logic under `src/x/` [Private folder] that assembles multi-source context and invokes the LLM.
- **Data & Persistence Tier**: Appwrite (authentication, user preferences, RPU counters) + external market/news APIs.

Communication between tiers is asynchronous and promise-based. All AI calls are gated by the RPU/MRPU handler before any external inference is performed.

## 7. Resource Economy (RPU / MRPU)

A distinctive engineering feature is the dual-counter resource system:

- **RPU** (Request Processing Units) – current consumption counter.
- **MRPU** (Maximum Request Processing Units) – hard limit per user.

Before any AI-powered command executes, the system invokes the following handler:

```typescript
export async function PRUxMRPU_handler(incrementValue?: number) {
    const { setUpdateUserData, updateUserData } = useUserData.getState();

    try {
        const res = await areRPUandMRPUEqual();

        if (res === 'not equal') {
            // Await the incrementRPU call directly
            const incRes = await incrementRPU(incrementValue);
            if (incRes === true) {
                setUpdateUserData(!updateUserData);
                return true;
            }
        } else if (res === 'equal') {
            return 'limitWarning';
        } else {
            console.error('Unexpected result when comparing RPU and MRPU:', res);
            return undefined;
        }
    } catch (error) {
        console.error('Error occurred during RPU check/increment:', error);
        return undefined;
    }
}
```

Most prediction and signal commands cost **5 RPU**. When RPU reaches MRPU, the system returns a limit-warning response and refuses further inference. This mechanism serves both as a cost-control layer for the LLM provider and as a pedagogical device that teaches users the scarcity of high-quality AI analysis.

## 11. Forecast Engine – End-to-End Pipeline

The most sophisticated component is the single-asset forecast pipeline (`runForecastCoin`).

### Step-by-step execution flow:

1. **News Acquisition**  
   Parallel fetches from NewsAPI for the queries “crypto”, “cryptocurrencies”, and “bitcoin”. Articles are reduced to `{title, description}` pairs.

2. **Macro Context**  
   Invocation of `runMarketInsights()` to obtain the current global market state vector.

3. **Asset-Specific Insights**  
   Call to `coinInsights(coin)` that retrieves technical and fundamental descriptors for the target asset.

4. **Prompt Assembly**  
   All three data sources are injected into a carefully engineered prompt template (`GET_forecast_prompt`).

5. **LLM Inference**  
   The assembled prompt is sent to the Google GenAI model via `AI_model()`. The response is cleaned of markdown fences and parsed as JSON.

6. **Structured Output**  
   The resulting object conforms to the `Forecast` interface and is rendered into seven distinct ASCII tables.

### Forecast Interface

```typescript
interface ExpectedDuration {
    value: number;
    unit: string;

interface Recommendations {

    timestamp_utc: string;

export interface Forecast {
    coin_name: string;
```

### Forecast Pipeline Implementation (core logic)

```typescript
async function runForecastCoin(coin: string) {
    // STEP 1: GET GLOBAL NEWS (fundamentals)
    async function fetchNews(query: string) {
        const apiKey = import.meta.env.VITE_NEWS_API_KEY;
        const url = `https://corsproxy.io/?https://newsapi.org/v2/everything?q=${encodeURIComponent(query)}&language=en&pageSize=50&apiKey=${apiKey}`;
        // ... fetch and map to {title, description}
    }

    async function getAllNews() {
        const [crypto, cryptocurrencies, bitcoin] = await Promise.all([
            fetchNews("crypto"),
            fetchNews("cryptocurrencies"),
            fetchNews("bitcoin"),
        ]);
        return [...crypto, ...cryptocurrencies, ...bitcoin];
    }

    const todaysMarketNews = await getAllNews();

    // STEP 2: GET MARKET INSIGHTS (fundamentals)
    const marketInsights = await runMarketInsights();

    // STEP 3: GET THE REQUESTED COIN INSIGHTS (technical)
    const requestedCoinInsights = await coinInsights(coin);

    // STEP 4: MERGE & PASS RESULTS OF STEP [1,2,3] TO BE AI-ANALYZED
    const merged_prompt_with_fetched_data = GET_forecast_prompt({
        todaysMarketNews,
        marketInsights: marketInsights as MarketInsights,
        requestedCoinInsights
    });

    // STEP 5: Send the collected data to AI model
    const AI_response = await AI_model(merged_prompt_with_fetched_data);
    const cleanJson = AI_response?.replace(/^```json\n/, '').replace(/\n```$/, '');
    const data = JSON.parse(cleanJson ? cleanJson : "{}");

    return data;
}
```

This schema enforces a minimum information set that any responsible trading recommendation should contain: entry, risk parameters, reward parameters, time horizon, confidence, and explicit risk disclosure.

## 12. AI Model Integration and Prompt Engineering

The LLM client resides in `src/x/lib/AI/AI_model.ts`. Prompts are versioned and stored under `src/x/lib/AI/prompts/`.

Prompt engineering follows best practices:

- Clear role assignment (“You are a quantitative crypto research analyst…”).
- Explicit output schema (JSON-only).
- Injection of raw market data, news headlines, and technical metrics as context.
- Instruction to enumerate red flags and assumptions.
- Temperature and sampling parameters controlled at the model call site.

The system deliberately forces the model to produce machine-parseable JSON rather than free-form prose, enabling reliable downstream formatting and future programmatic consumption.

## 16. Security, Rate Limiting, and Error Handling

- All sensitive operations require an active Appwrite session.
- RPU gating prevents unbounded LLM cost exposure.
- Network errors in news or market data fetches degrade gracefully (empty arrays are substituted).
- JSON parsing of LLM responses is protected with fallback empty objects.
- Password reset flows use dedicated, short-lived routes.

## 19. Command Reference with Example Outputs and Explanations

### 19.1 `atm predict insights`

**Purpose:** Provide a dated macro snapshot of the cryptocurrency market.  
**Cost:** 5 RPU  

**Key metrics returned:**

- Market capitalization and volume (absolute USD figures)
- BTC dominance percentage
- Sentiment score ∈ [0, 100]
- Qualitative trend and direction statements
- Numeric signal strength evaluation

**Interpretation guidance:**  
A sentiment score > 65 combined with a “Strong” signal classification typically indicates a constructive macro environment for long-biased strategies. Conversely, scores < 35 with negative classification favor caution or short bias.

### 19.2 `atm best long` / `atm best short`

**Purpose:** Surface the single highest-conviction directional opportunity.  

**Output structure:**

1. Ranked table (usually a single row).
2. Instructional tip linking to the deeper forecast command.

**Academic note:** This command implements a form of “best-idea” concentration, a well-documented phenomenon in active portfolio management research.

### 19.3 `atm forecast <SYMBOL>`

**Purpose:** Generate a complete, risk-managed trade plan.  

**Quantitative outputs of primary interest:**

| Field                        | Description                                      | Typical Range / Notes                  |
|-----------------------------|--------------------------------------------------|----------------------------------------|
| `risk_reward_ratio`         | Reward-to-risk ratio                             | Preferably ≥ 1.5                       |
| `confidence_score`          | Continuous self-assessed confidence              | [0, 1]                                 |
| `stop_loss_distance_pct`    | Distance from entry to stop-loss                 | Percentage                             |
| `take_profit_distance_pct`  | Distance from entry to take-profit               | Percentage                             |
| `expected_duration`         | Estimated holding period                         | Value + unit (e.g., 4–7 days)          |

**Example interpretation (hypothetical):**  
Entry $62,450 · SL $60,100 (−3.76 %) · TP $68,200 (+9.21 %) · RR 2.45 · Confidence 0.78 · Duration 4–7 days.  

Such a profile would be considered a high-quality intermediate-term long setup under conventional risk-management frameworks.

## 20. Quantitative Considerations and Performance Vectors

While live performance statistics are outside the scope of this documentation (the system is a decision-support tool rather than an automated trading engine), several quantitative design decisions merit explicit statement:

- Confidence scores are produced by the LLM under instruction to self-assess; they are not calibrated probabilities from a supervised model.
- Risk-reward ratios are computed deterministically from the three price levels returned by the model.
- Position sizing is deliberately left to the user; the system only suggests leverage and order type.
- All monetary figures are expressed in USD; percentage distances are calculated relative to the recommended entry.

**Future academic extensions could include:**

- Back-testing of historical forecasts against realized price paths.
- Calibration of confidence scores against empirical hit rates.
- Integration of realized volatility surfaces for dynamic position sizing.

## 21. Limitations, Assumptions, and Future Work

### Current Limitations

- Dependence on third-party news and market data APIs (availability and rate limits).
- LLM non-determinism (identical prompts may yield slightly different rationales).
- Absence of real-time order-book or on-chain flow data.
- No automated execution or brokerage connectivity.

### Core Assumptions

- Market data and news feeds are timely and approximately accurate.
- The LLM has been sufficiently instruction-tuned to respect the requested JSON schema.
- Users possess the domain knowledge to interpret risk parameters and size positions appropriately.

### Planned Enhancements

- Vector-store retrieval of historical analogous market regimes.
- Multi-model ensemble voting for higher robustness.
- User-configurable risk templates and position-size calculators.
- Export of forecasts to structured formats (CSV, JSON, PDF).

## 22. Conclusion

Automission (ATM) represents a deliberate synthesis of modern large-language-model capabilities, classical quantitative research workflows, and thoughtful human-computer interaction design. By presenting AI-generated market intelligence inside a professional terminal interface, enforcing resource scarcity, and insisting on structured, risk-aware outputs, the system elevates conversational AI from a novelty into a research-grade analytical instrument.

The architecture is modular, the code is typed, the outputs are transparent, and the resource economy is explicit. These characteristics make ATM suitable both for practical decision support and for academic examination of human-AI collaboration in financial domains.
